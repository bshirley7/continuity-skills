# Technical

## Generalized principles

- Design setup as a verifiable path from resource creation through scoped credentials and runnable example to observable success, preserving one-time secret warnings and recovery guidance.
- Make technical scope persistent by naming project, environment, service, resource, region, version, time range, live state, permission, and secret boundary wherever actions or evidence depend on them.
- Connect operational summaries to raw evidence and intervention: current health, distribution or trend, individual executions or incidents, exact timestamps and outcomes, then bounded recovery actions.
- Treat deployment as a lineage-aware boundary that shows current version, candidate version, source, age, configuration, runtime status, history, verification, rollback, and the consequence of promotion.
- For AI development, keep prompt or agent specification, model and tool configuration, dataset and evaluator contract, test results, deployment, monitoring, and revision identity in one traceable lifecycle.
- Use technical density to expose causality and control, not to signal expertise: labels, units, status, exact scope, copyable commands, and safe defaults must remain understandable to a new operator.

## Variation levers

- Use guided setup for first success and persistent configuration pages for repeat administration.
- Use code examples for programmable systems and structured forms for resource and permission setup.
- Use light themes for configuration and either light or dark themes for sustained monitoring.
- Use timelines and histories for deployment lineage and tables for execution evidence.
- Use staged navigation for prompt, evaluate, deploy, and monitor lifecycles.

## Tensions and tradeoffs

- Copyable credentials accelerate setup while increasing exposure risk.
- Expert density speeds repeat work while intimidating new operators.
- Live evidence improves awareness while changing during inspection.
- One-click deployment reduces friction while obscuring consequence.
- Integrated AI lifecycle views preserve lineage while becoming spatially complex.

## Failure modes

- Setup ends before a verifiable successful request.
- Secrets are shown without one-time warning, scope, or secure recovery.
- Evidence lacks project, environment, resource, time, or live-state binding.
- Deployment omits source, version, verification, history, or rollback.
- AI evaluation is detached from prompt, dataset, model, or revision.
- Agent execution lacks action history, proof, checkpoint, or runtime state.

## Anti-patterns

- Credential copy with no exposure warning.
- Environment hidden in a menu.
- Logs without exact time scope.
- Deploy buttons without target or version.
- Status color without text.
- Evaluation scores without dataset or evaluator identity.
- Agent completion claims without verification evidence.
- Technical complexity used as decoration.

## Acceptance and review questions

- Does setup end in observable success with secure credential guidance?
- Are project, environment, resource, version, time, permission, and secret scopes explicit?
- Can users move from health to evidence to bounded intervention?
- Does deployment preserve source, version, state, history, verification, rollback, and consequence?
- Are AI specification, configuration, dataset, evaluation, deployment, monitoring, and revision traceable?
- Can a new operator understand labels, units, status, commands, and defaults?
