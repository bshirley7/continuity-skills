# Accessibility language

## Generalized principles

- Name accessibility settings by the interface behavior they change—text size, contrast, motion, sound, captions, timing, focus, input, or navigation—without diagnosing, stigmatizing, or requiring users to justify the preference.
- For every preference, state the resulting effect, scope, current value, immediacy, persistence, interaction with device or organization settings, and how to restore the prior state.
- Describe alternative input and commands with the same canonical action names used by visible controls; identify keys or method, platform variation, scope, current availability, conflicts, and an equivalent path.
- When time, verification, or security constraints interrupt a task, explain the reason, time remaining or reset behavior, retained work, safest continuation, alternative supported method, and escalation path without blaming the user.
- Offer accommodations and human assistance through ordinary, respectful language that describes the available path, expected effort, timing, privacy, and outcome without requiring disclosure of disability or presenting support as an exception.
- Treat visible accessibility language as one layer of evidence only; separately verify programmatic names, roles, states, reading order, announcements, focus, keyboard behavior, captions, and assistive-technology output before claiming accessibility.

## Variation levers

- Integrate common preferences into ordinary appearance, sound, navigation, and input settings while retaining one searchable accessibility index.
- Use live preview when a change is safe and reversible; use a descriptive example when preview could be disorienting.
- Group command help by task and context rather than by key alone.
- Offer self-service alternatives first and a clearly labeled human-support path for blocked or high-consequence cases.
- In managed environments, show personal choice, inherited default, enforced policy, and available request path together.

## Tensions and tradeoffs

- Behavior-based labels reduce stigma while making a unified accessibility area harder to discover.
- Detailed explanations improve control while increasing reading burden.
- Immediate preview supports understanding while potentially causing motion, contrast, or orientation discomfort.
- Security constraints protect accounts while blocking users who cannot complete one verification method.
- Centralized settings improve discovery while separating preferences from the context where users need them.
- Friendly support language reduces anxiety while obscuring formal accommodation rights or escalation.

## Failure modes

- A setting is named for a diagnosis instead of the behavior it changes.
- The effect, scope, persistence, or reset path is missing.
- Keyboard help uses action names that differ from visible controls.
- A timeout warning provides no extension, saved-state, or recovery information.
- Verification failure is framed as user error with no alternative method.
- Users must disclose disability to access an available alternative.
- Visible accessible wording is treated as proof of programmatic accessibility.

## Anti-patterns

- For disabled users.
- Special needs mode.
- Normal versus accessible.
- Keyboard shortcut without visible equivalent.
- Session expired with lost work.
- Verification failed, try again.
- Contact support without channel or expectation.
- Accommodation requires diagnosis.
- Accessibility claim from screenshots.
- Preference reset hidden behind account deletion.

## Acceptance and review questions

- Are settings named by changed behavior without diagnosis, stigma, or required justification?
- Does each preference state effect, scope, value, immediacy, persistence, precedence, and reset?
- Do alternative-input instructions match canonical action names and identify method, platform, scope, availability, conflicts, and equivalent paths?
- Do time and verification interruptions explain reason, remaining time or reset, retained work, continuation, alternatives, and escalation?
- Are accommodations ordinary, respectful, specific about effort, timing, privacy, and outcome, and available without disability disclosure?
- Have programmatic names, roles, states, order, announcements, focus, keyboard behavior, captions, and assistive output been separately verified?
- Can users locate accessibility options both through a central index and at the point where the behavior occurs?
