# Comprehension

## Generalized principles

- Build an explicit semantic definition around important information: name the object, define the measure or status, state scope and time basis, identify source and freshness, and show ownership or authority before users act on it.
- Preserve the relationship between summary and detail by keeping the selected object, current filters, comparison basis, and surrounding context visible while definitions, formulas, history, or exceptions open nearby.
- Organize unfamiliar concepts by user purpose and outcome before exposing system structure or syntax, using stable category names, short definitions, and concrete examples that show where each concept applies.
- Connect every configuration choice to its effective scope, default or inherited state, dependency, pending-versus-saved status, and observable consequence through preview, example behavior, or a concise change summary.
- Teach workflows as a causal sequence: explain prerequisites, what each stage produces, who participates, expected timing, current progress, remaining work, and what the next transition will make true.
- Make requirements visible before interaction, express them in plain language, reflect validity in control state, and point incomplete or invalid status to the exact missing field, section, person, or prerequisite.
- Translate consequential reviews into the underlying people, resources, dates, money, permissions, and obligations, preserving editability and a preview of the exact artifact before commitment.
- Distinguish live, demo, draft, pending, active, incomplete, complete, delayed, and unavailable states with persistent labels and definitions so visual similarity cannot imply equivalent authority or readiness.
- Use progressive disclosure to reduce initial load without hiding essential meaning: keep identity, state, scope, consequence, and next action in the primary layer, then reveal formula, provenance, history, and advanced controls on demand.
- Provide multiple learning routes for complex domains—guided checklist, example, preview, concise help, and direct action—while keeping them aligned to the same terminology and product model.

## Variation levers

- Use a table when users compare many objects, an adjacent inspector when they need context-preserving detail, and a dedicated review when commitment requires full focus.
- Use inline definitions for unfamiliar high-frequency terms, tooltips for secondary clarification, and linked documentation for long or exceptional rules.
- Use examples for behavioral rules, previews for visual configuration, formulas and queries for analytic provenance, and change summaries for consequential settings.
- Use a linear stepper for dependent stages, a checklist for independently completable setup tasks, and a timeline for deadline-driven multi-party work.
- Use persistent environment or data-origin labels when demo, test, branch, draft, and live contexts can otherwise be confused.
- Use completion counts for bounded work, status distributions for many objects, and explicit exception links for missing or invalid inputs.
- Use plain-language labels first and retain expert terms in supporting detail when domain precision matters.
- Use skip when personalization is optional, save-and-exit for resumable work, and hard blocking only for true prerequisites.

## Tensions and tradeoffs

- More definitions improve accuracy while increasing density and scan time.
- Progressive disclosure reduces initial load while risking hidden context or consequence.
- Plain language improves accessibility while expert terminology preserves domain precision.
- Live preview explains effect while it may imply publication before save.
- Guided setup teaches the model while delaying direct access for experienced users.
- Persistent state labels reduce ambiguity while adding visual noise.
- Technical provenance supports trust while overwhelming non-technical users.
- Summaries accelerate review while omitting exceptions that change a decision.

## Failure modes

- A metric, status, setting, or workflow stage lacks definition, scope, time basis, source, or authority.
- Opening detail loses the selected object, filters, comparison, or place in the larger workflow.
- System-oriented categories are presented before users understand their purpose or outcome.
- A configuration control hides default, inheritance, dependency, save state, or downstream effect.
- A stepper shows position without explaining prerequisites, outputs, participants, timing, or next-state consequence.
- Invalid or incomplete status blocks progress without locating what must change.
- A consequential review omits affected people, resources, dates, money, permissions, or obligations.
- Demo, draft, pending, live, delayed, and complete states appear equivalent.
- Progressive disclosure hides identity, state, scope, consequence, or next action.
- Tutorials, examples, previews, and help use conflicting terminology or models.

## Anti-patterns

- Showing a number and trend arrow without definition or comparison basis.
- Using an unexplained status badge as the only description of readiness.
- Hiding metric meaning in a separate glossary users must leave the task to find.
- Presenting raw technical configuration without an example or preview.
- Using a progress bar that does not reveal completed and remaining work.
- Disabling continue without stating the unmet constraint.
- Calling a draft live because the preview looks complete.
- Summarizing an agreement without parties, dates, money, or obligations.
- Treating demo data as indistinguishable from production data.
- Teaching one object model in onboarding and using different labels in the application.

## Acceptance and review questions

- Are object, definition, scope, time basis, source, freshness, owner, and authority explicit where relevant?
- Can users move between summary and detail without losing selection, filters, comparison, or workflow context?
- Are unfamiliar concepts organized by user purpose and illustrated with concrete examples?
- Do configuration choices reveal defaults, inheritance, dependencies, save state, and observable consequences?
- Does each workflow stage explain prerequisites, output, participants, timing, progress, and next-state effect?
- Do invalid and incomplete states point to the exact missing field, section, person, or prerequisite?
- Does consequential review expose affected people, resources, dates, money, permissions, and obligations?
- Are demo, draft, pending, active, incomplete, complete, delayed, and unavailable states distinguishable?
- Does the primary layer retain identity, state, scope, consequence, and next action?
- Do guided, example, preview, help, and direct-action paths use one consistent terminology and model?
