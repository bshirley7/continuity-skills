# Continuity Design

Work entirely offline from the installed reference catalog. Do not browse for design examples or access an external maintenance system from this skill.

Read [workflow handoffs](../../references/workflow-handoffs.md), [output quality rubrics](../../references/output-quality-rubrics.md), [decision lenses](../../references/decision-lenses.md), and the [Continuity contract](../../references/continuity-contract.md). Machine state and approval boundaries remain authoritative.

## Preconditions

1. Run `continuity project doctor` and confirm the `design` collection is enabled and healthy.
2. Retrieve relevant captures, trusted memory, PRDs, feature requests, product documentation, application structure, existing interface or artifact context, and any existing `docs/design/design.md`. Use that evidence to reconstruct the working title, intent, audiences, and target modalities; do not require the user to know or supply those fields.
3. Read [catalog.json](references/catalog.json). Treat industry, section, theme, message-structure, and lens labels as optional internal retrieval aids, not questions the user must answer or concepts the design must name. Read category references when the user explicitly supplies a matching concept or the project context makes a reference materially useful. Category packs refine their foundation; they do not replace it. Apply [lens-routing.json](references/lens-routing.json) privately as a review aid when lenses are not explicit. Record inferred checks and pack provenance in private machine state without requiring the design document to name them.
4. Treat existing favorable behavior and explicit non-regression requirements as constraints, not as disposable context.
5. Read [creative direction methodology](references/creative-direction-methodology.md). When creating, materially reshaping, or generating an artifact from a direction, also read [distinctive expression methodology](references/distinctive-expression-methodology.md). Assess the existing design before proposing change; do not invent findings for surfaces or artifacts you did not inspect.
6. For React or React-based web work, inspect the actual implementation system before calling a direction implementation-facing: framework and versions, package manifest, styling and token systems, installed UI, motion, data, and icon libraries, reusable component roots, Storybook or preview harnesses, and local asset roots. Record this as evidence-bearing `implementation_context`; never infer installation from familiarity or add a dependency during design work.

## Direction workflow

1. Prepare a private design input from [design-input.example.json](references/design-input.example.json), using [distinctive-expression.example.json](references/distinctive-expression.example.json) as the direction-level shape when distinctive expression is in scope. Derive its working title, intent, audiences, and targets from the request and retrieved project evidence. Treat them as agent-authored working fields, not user intake requirements. Record inspected evidence, current strengths, gaps, design debt, uncertain assumptions, preservation requirements, non-goals, validation criteria, and unresolved material questions. For every material insight that changes the design, add an `insight_decisions` record connecting it to a concrete design response, affected surfaces and states, and observable evidence. Do not turn every observation into a UI element. Preserve the user's natural language. Do not ask the user to classify the work by industry, section, theme, message structure, lens, style taxonomy, or other design terminology. Use inferred categories privately when they materially improve retrieval and record their provenance; do not expose them as user requirements. Use `consequences`, `workflow_signals`, `interaction_signals`, and `risk_signals` internally when those conditions are evident.
2. Proceed with the strongest evidence available. Do not stop merely because the title, intent, audience, target, style, or desired approach is incomplete. Choose a provisional scope, make uncertainty visible, and produce useful directions. Ask concise questions alongside the result when an answer would materially improve the next revision; incorporate later answers through normal design revision.
3. Record `direction_count`, its material `direction_count_basis`, and a `direction_assessment` naming material ambiguities and any resolved by inspected evidence:
   - one only when both the organizing idea and the expressive posture are settled by evidence or an explicit user choice;
   - two when one material tradeoff remains;
   - three when multiple materially different approaches remain plausible.
   Do not use document completeness, safety coverage, or a polished first idea as evidence that the organizing idea is settled. One direction is invalid while a recorded material ambiguity remains unresolved.
4. Author project-specific directions from the intent, evidence, current design, audience, constraints, preservation requirements, and consequential context. Supply the directions in the private input; do not rely on the CLI's recovery fallback as completed creative work. Make directions differ in organizing idea, experience architecture, expression, and tradeoffs—not merely colors, fonts, or decoration. Give each direction a recognizable creative signature grounded in the product's purpose, and state how that signature appears in composition, type, color, form, imagery, motion, or voice as applicable. For created or materially reshaped work, supply `creative_provenance` and `distinctive_expression`: derive subject-world cues from inspected or supplied project evidence, label creative inference honestly, take one bounded aesthetic risk, reject interchangeable defaults, define a concrete expression system, allocate an `expression_budget`, and name representative compositions and uniqueness checks. Infer and record a `design_register` of `brand`, `product`, or `mixed`; use a concrete `usage_scene` to calibrate the work; and choose a separate `color_commitment` of `restrained`, `committed`, `full-palette`, or `drenched` so expression weight does not automatically mean saturation. Record a `target_weight` and `exploration_ceiling` from `0.0` to `1.0`, whether the posture is inferred or user-supplied, and the project-specific rationale. Infer a useful posture when the user does not provide one; do not turn any of these fields into intake requirements. Use `boundary-study` to label deliberately over-normal exploration without weakening accessibility, readability, truthful state, authority, recovery, preservation, responsive integrity, or provenance. Define a `brand_signature` that turns the identity premise into a primary carrier, recurring carriers, utility, quiet, and campaign modes, subject-derived semantic tokens, a context transformation matrix, prohibited substitutions, and recognition tests. Require the signature to survive beyond one hero and generate a family of surfaces without repeating one layout. Complete an `anti_reflex_review` that rejects both the obvious category default and the fashionable counter-default when neither is supported by the subject. For implementation-facing targets, compile a stack-grounded `implementation_system` covering tokens, type, layout, motion, component recipes, and hardening checks. Link the expression to its provenance IDs so these decisions render into `design.md` and remain available to later planning and artifact review. Safety rules constrain the concept; they must not become the concept or bury its aesthetic point of view. Do not turn catalog taxonomy into the concept, outline, headings, or vocabulary unless the user explicitly requested it. Use inferred packs as silent creative context and review checks. Resolve tensions through [composition precedence](references/composition-precedence.json); never resolve them by prompt order or averaging. Translate the direction into its target-appropriate dimensions from [design grammar](references/design-grammar.md), content rules, audience strategy, prototype boundaries, component and pattern rules, implementation guidance, acceptance and drift checks, and prohibited patterns. Apply [prototype integrity](references/prototype-integrity.md) when a prototype, representative content, or multiple audiences are involved. Autonomy, comprehension, accessibility, refusal, correction, exit, and recovery remain non-negotiable safeguards rather than stylistic callouts.
5. Refine each authored direction through the ordered passes in [distinctive expression methodology](references/distinctive-expression-methodology.md): provenance grounding, divergent exploration, boundary push, contextual review, restraint edit, responsive transformation, and artifact critique. Infer the useful review perspectives from the project, target, consequences, and installed references; never require the user to name lenses or repeat their taxonomy in the result. A contextual review is complete only when `contextual_reviews` records why each material perspective applies, its concrete finding, the resulting design response, favorable behavior preserved, and an observable verification. Do not satisfy this with a generic statement that the design was reviewed. Record explicit routing only when the user or project evidence names the perspective; otherwise label it inferred. Before selection, complete and record the first six passes with what changed, what was deliberately preserved, and any unresolved issue. Keep artifact critique pending until representative HTML, PNG, document, image, or other target-native output exists. If artifact critique changes the approved direction, create a new revision and require exact approval rather than silently changing the contract.
   Treat natural requests to make a direction bolder, quieter, distilled, typeset, laid out, colorized, animated, delightful, hardened, or polished as bounded refinement intents—not separate skills or permission to implement. Change the smallest relevant portion of the contract, re-run every affected downstream pass, preserve recorded favorable behavior, and create a new exact revision when an approved contract changes.
6. Present directions with progressive disclosure. Lead with a compact decision view: reconstructed problem, current strengths, recommended direction, creative signature, principal tradeoff, preservation promise, and material unknowns. Put detailed grammar, safeguards, implementation constraints, and drift checks in the durable contract beneath it. Clarity is not completeness removed; it is the important choice made visible before supporting detail.
7. Apply category-pack acceptance questions as review gates. When foundation and category guidance differ in specificity, use the category guidance without weakening foundation safety or accessibility constraints.
8. Apply every pack according to its `modalities` entry for the requested target:
   - `validated` means the pack contains direct evidence for that modality;
   - `inferred` means apply only its `modality_independent_principles` and label the application inferred;
   - `not-applicable` means do not apply that pack to the target.
   Report `mixed` when a target combines validated and inferred packs. An empty modality-independent list supplies no inferred guidance. `campaign` and `platform` are evidence contexts used by applicable packs, not additional publication targets or implementation authority.
9. For UI or web work, default to a `complete-prototype` completion contract unless the user explicitly asks for exploration only. Before drafting, provide an evidence-backed component map classifying each material need as `reuse`, `compose`, `extend`, `custom`, or `missing-capability`, with required states, responsive transformation, accessibility behavior, and custom expression. Provide an asset strategy for every material image, illustration, diagram, icon family, texture, or deliberate omission. Existing, supplied, and derived assets require source references. A library supplies proven behavior and semantics; it must not silently supply the product's finished aesthetic.
10. Run `continuity design draft --input <design-input.json>`.
11. Require the user to select a direction or explicitly combine directions with `continuity design select`.
12. For a selected complete UI prototype, create the ignored private package under `.continuity/private/designs/<design-id>/<revision>/`. Use the project's installed React framework, configured UI libraries, tokens, components, and preview harness where safely available. Do not add production routes, modify application behavior, install dependencies, or include the prototype in production build inputs. Produce a coherent representative page or smallest complete workflow, representative content, required local assets, relevant states, and desktop, tablet, and mobile captures. A hero plus generic cards is not a complete composition.
13. Create a version 2 manifest from [complete-prototype-manifest.example.json](references/complete-prototype-manifest.example.json). Bind source files, captures, implementation context, component map, asset strategy, selected design hash, claims, decided insights, viewports, states, and validation evidence. Run `continuity design prototype-validate --manifest <manifest.json>` before approval.
14. Complete artifact critique against the target-native renders. Run `scripts/artifact-browser-probe.js` in every required browser viewport and treat its craft findings as evidence, not automatic aesthetic bans. Check signature recognition, persistence beyond the opening composition, quiet-mode continuity, family-generation range, subject specificity, library-default leakage, content authenticity, asset quality, type craft, spacing rhythm, component coherence, state coverage, responsive transformation, accessibility, and document-to-artifact drift. Remove the logo, primary accent, imagery, or motion where practical and verify that the carrier relationships remain recognizable. Record every material finding with artifact location, severity, response, verification, and any evidence-backed intentional override. A `critical` or unresolved `error` finding blocks implementation-facing maturity. If critique changes the direction or durable contract, create a new revision, regenerate the affected artifact, and validate again. Never leave artifact critique pending when rendered artifacts exist.
15. Present the refined exact private draft and its SHA-256 hash. Do not promote it without exact approval.
16. After the user approves the exact ID, revision, and hash, run `continuity design approve`. This writes `docs/design/design.md` and `.continuity/design.json`.
17. Re-run `continuity design artifact-validate --manifest <manifest.json>` against the approved record. Do not call an artifact implementation-facing unless both candidate and approved validation pass. The private prototype remains design evidence and never becomes production implementation automatically.

## Approval boundary

The required authorization text is printed by `design select` and must name the design ID, revision, and exact hash. Approval authorizes publication of that exact document only. It does not create, approve, revise, dispatch, or execute a goal.

A later design revision creates new evidence. It never changes an existing goal automatically. When implementation is later planned, include the approved design ID in `design_ids`; `$continuity-plan` derives and hash-binds the exact design revision.
