# VS Code, Codex, and Claude Code

This guide describes the supported project-local setup for using Continuity
from the Codex and Claude Code VS Code extensions. It applies to native Windows,
macOS, and Linux; Windows launcher details are in [Native Windows Setup and
Operation](windows.md).

## Canonical Project Contract

Continuity is installed into each project. Do not copy one project's generated
configuration or private state into another project.

```text
AGENTS.md                              shared project instructions
.agents/skills/                        canonical Continuity skills
.agents/skills/continuity-local/       hash-bound project behavior
.agents/continuity/                    project-local CLI and contracts
CLAUDE.md                              generated import of AGENTS.md
.claude/skills/                        generated byte-identical Claude adapters
.claude/commands/                      generated slash-command compatibility shims
.continuity/private/                   ignored operational state; not startup context
```

Codex discovers repository skills in `.agents/skills/` from the working
directory up to the Git root. Claude Code natively discovers project skills in
`.claude/skills/`; Continuity regenerates that tree from the canonical
`.agents/skills/` tree and `project doctor` fails if an adapter is missing or
different. `CLAUDE.md` uses `@AGENTS.md`, the documented Windows-safe way to
share the same project instructions without a symlink.

Do not edit `.claude/skills/`, `.claude/commands/`, or the managed block in
`CLAUDE.md`. Edit a suite-owned canonical skill in the suite checkout, or update
project behavior through `project configure`, and then reinstall or reconfigure.

## Configure Both Surfaces

Install the official Codex and Claude Code extensions, review the project, and
then trust the project folder in VS Code. Restricted Mode intentionally disables
agents and extensions that can execute project code. Do not override an
extension's untrusted-workspace declaration to make Continuity run in an
unreviewed repository.

Enable both project adapters while leaving scheduling and execution disabled:

```json
{
  "agent_surfaces": {
    "primary": "codex",
    "enabled": ["codex", "claude-code"]
  },
  "scheduler": {
    "provider": "none"
  },
  "execution_enabled": false
}
```

Apply the file with the project-local CLI and run doctor. On native Windows,
use the CMD launcher so PowerShell execution policy cannot hide a healthy
installation:

```powershell
& "$Project\.agents\continuity\bin\continuity.cmd" `
  --project-root $Project --json project configure `
  --answers-file C:\path\to\agent-surfaces.json --actor $env:USERNAME

& "$Project\.agents\continuity\bin\continuity.cmd" `
  --project-root $Project --json project doctor
```

Doctor must report `healthy: true`. Execution remains false; enabling an agent
surface does not enable scheduling, dispatch, GitHub mutation, or merging.

## Start or Reload the Agents

Project instructions are session-start context. After the first install, after
adding `CLAUDE.md`, or after changing `AGENTS.md`, start a new Codex and Claude
Code conversation. Do not rely on a conversation that began before the files
existed.

Skill changes are normally detected live. If a skill does not appear:

1. End the existing agent conversation.
2. Run **Developer: Reload Window** in the VS Code Command Palette.
3. Start a new conversation in the project root.
4. Run `project doctor` again.

Codex exposes discovered skills through `/skills` and `$` mentions. Claude Code
exposes them through `/skills` and `/skill-name`; `/memory` shows the loaded
`CLAUDE.md` files. A newly created top-level `.claude/skills` directory requires
a Claude session restart before it can be watched.

Expected entry points include:

```text
Codex:       $continuity, $continuity-workflow, $continuity-capture
Claude Code: /continuity, /continuity-workflow, /continuity-capture
```

Use the same pattern for `triage`, `memory`, `roadmap`, `plan`, `dispatch`,
`execute`, `test`, `merge`, `report`, and `share`. A skill selector proves
discovery; it does not authorize any operation. The current machine handoff
from `continuity workflow status` and persisted approval records remain the
authority.

## Working Directory and Multi-Root Workspaces

Starting either CLI in a subdirectory of an enrolled Git repository is
supported: both products walk toward the repository root for project skills or
instructions. The project-local Continuity CLI also walks upward to
`.continuity/config.json`.

For scripts, VS Code tasks, and every multi-root workspace, always pass the
absolute `--project-root`. Never infer the target from the terminal's last
directory or from the currently visible editor.

The supported multi-root policy is one active Continuity project per agent
conversation:

- Prefer a separate VS Code window for each project.
- If a multi-root workspace is necessary, put the target project first, start a
  fresh conversation for that project, and pass its exact root to every CLI
  command.
- Do not use one conversation to mutate two enrolled roots. Claude Code grants
  file access to additional workspace folders, but most project configuration
  from those additional folders is not startup context. Codex and extension
  behavior can also change as roots or editor context change.
- Adding an untrusted folder to a trusted multi-root workspace can put the whole
  workspace into Restricted Mode. Review and trust every root separately.

These rules avoid a silent first-folder or active-editor selection and keep the
project ID, locks, approvals, and private state bound to one root.

## Simultaneous Agents

Codex, Claude Code, terminals, and a configured scheduler may read the same
project concurrently. Every mutating project-local CLI invocation takes the
same native process lock, and narrower workflow locks and remote leases still
apply. Mutations therefore serialize or fail closed; conversation history is
never a lock and never approval evidence.

Do not let two agents hand-edit generated adapters or canonical JSON files.
Route state changes through the project-local CLI. If an agent reports lock,
lease, stale-state, or approval contention, inspect `workflow status` and
resolve the canonical condition instead of bypassing it.

## Private State and Chat Context

`.continuity/private/` and `.continuity-portfolio/` are ignored and are not
imported by `AGENTS.md`, `CLAUDE.md`, skill metadata, or slash-command shims.
Raw captures, credentials, approval receipts, scheduler records, and recovery
state are therefore not automatic startup context.

An agent with trusted workspace tools can still read a private file when a
specific workflow requires it or when a user explicitly asks for it. Trust is
not a secrecy sandbox. Do not attach `.continuity/private/`, add it to editor
context, place secrets in prompts, or disable the project's ignore rules.
Reports and shared-note flows must use their existing allowlists and redaction
paths.

## Remote Development

WSL, Dev Containers, Remote SSH, tunnels, and Codespaces use a remote extension
host and a remote filesystem. They are not the same runtime as a native Windows
workspace, even when the VS Code user interface runs on Windows.

- Install or enable the agent extensions in the remote window and use
  **Developer: Show Running Extensions** to confirm where each extension runs.
- Install Continuity into the remote checkout and rerun the installer with the
  remote platform's Python. Do not reuse a launcher bound to Windows Python.
- Use `continuity.cmd` or `continuity.ps1` only in a native Windows workspace;
  use the extensionless launcher in Linux, WSL, containers, and typical SSH
  hosts.
- Ignored local private state does not travel with Git. Restore it only through
  the verified backup flow; never copy it through agent chat.
- A remote clone has its own local locks. Cross-clone exclusivity requires the
  configured remote lease and cannot be replaced by a VS Code workspace lock.

Remote Development must pass the acceptance suite on its actual host OS. A
native Windows pass is not evidence for WSL, Linux, macOS, a container, or a
remote server.
